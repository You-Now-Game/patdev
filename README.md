# Patina Studio — веб-приложение

Веб-версия сервиса контроля хода ремонта: клиент следит за готовностью объекта,
строитель вносит прогресс, визиты и материалы. Реализовано по макету
`maket_patina_studio_web_v2.pdf` (9 экранов, роли «Клиент» / «Строитель»).

## Стек

- **Next.js 15** (App Router, TypeScript, Server Actions)
- **PostgreSQL + Prisma 5** — схема данных и миграции
- **Auth.js (NextAuth v5)** — аутентификация по телефону/e-mail и паролю, роли `CLIENT` / `BUILDER` / `ADMIN`
- **Tailwind CSS** — вёрстка по макету
- Фото объектов — локальное хранилище `public/uploads` (см. «Хранилище файлов» ниже)

## Возможности

**Клиент (только просмотр):**
- Объект — фото, характеристики, общая готовность
- Типы работ — прогресс по 5 этапам (дизайн-макет → черновые → технические → рабочие → чистовые), вид «Круг» и «Диаграмма»
- Время — журнал визитов строителя, фильтр по этапам, статистика (визитов/часов/последний визит)
- Материалы — список по этапам с остатками

**Строитель (редактирование, изменения сразу видны клиенту):**
- Объекты — список, создание нового объекта, привязка клиента по e-mail/телефону, загрузка фото
- Типы работ — слайдеры прогресса 0–100% с шагом 5%, live-превью «как увидит клиент»
- Время — добавление/редактирование/удаление визитов, прогресс этапа обновляется автоматически
- Материалы — вкладки по этапам, добавление/переименование/удаление позиций, остатки

**Администратор** (`/admin/login`, отдельный вход, не связан с публичным
переключателем ролей):
- Пользователи — список всех аккаунтов (клиент/строитель/админ), создание
  новых аккаунтов строителей и админов, удаление аккаунтов
- Объекты — обзор всех объектов по всем строителям (только просмотр)

Публичная регистрация (`/register`) доступна **только для роли «Клиент»** —
это осознанное ограничение: аккаунты строителей и администраторов заводит
только администратор через `/admin/users`, чтобы к редактированию чужих
объектов не мог получить доступ кто угодно самостоятельной регистрацией.
Роль аккаунта хранится в БД — переключатель на странице входа лишь выбирает,
в какой кабинет войти, и система проверяет, что роль аккаунта совпадает.

## Быстрый старт (локально)

Требуется Node.js 20+ и Docker (для локального PostgreSQL).

```bash
cp .env.example .env
# сгенерировать AUTH_SECRET: openssl rand -base64 32 (и вписать в .env)

docker compose up -d db
npm install
npm run db:migrate:dev   # создаёт таблицы
npm run db:seed          # тестовые данные (см. ниже)
npm run dev
```

Приложение откроется на http://localhost:3000.

**Тестовые аккаунты после `npm run db:seed`:**

## Структура проекта

```
prisma/schema.prisma      — модель данных (User, ConstructionObject, WorkProgress, Visit, Material)
prisma/migrations/        — SQL-миграции для PostgreSQL
prisma/seed.ts            — демо-данные
src/lib/auth.config.ts    — edge-safe часть конфигурации Auth.js (используется в middleware)
src/lib/auth.ts           — полная конфигурация Auth.js (Credentials-провайдер, bcrypt)
src/lib/actions/          — Server Actions (мутации: объекты, прогресс, визиты, материалы, auth)
src/lib/queries.ts        — серверные запросы к БД для страниц
src/lib/storage.ts        — сохранение фото объектов (локальный диск)
src/middleware.ts         — защита /client/*, /builder/* и /admin/* по роли
src/app/(login|register)  — публичные страницы (только роль "клиент")
src/app/admin/login       — отдельный вход администратора
src/app/client/*          — кабинет клиента
src/app/builder/*         — кабинет строителя
src/app/admin/(dashboard) — панель администратора (пользователи, объекты)
src/components/           — UI-компоненты (ui/, layout/, auth/, client/, builder/)
```

## Хранилище файлов

По умолчанию фото объектов сохраняются на диск в `public/uploads` (см.
`src/lib/storage.ts`). Для продакшена с несколькими инстансами/без персистентного
диска замените реализацию `saveObjectPhoto()` на загрузку в S3-совместимое
хранилище (Yandex Object Storage, Selectel, AWS S3 и т.п.) — вызывающий код
(server actions) менять не нужно, функция остаётся с той же сигнатурой.

Если деплой идёт через Docker (см. `docker-compose.yml`), для `public/uploads`
уже настроен volume `patina_uploads`, чтобы фото не терялись при пересборке
контейнера.

## Деплой

### Вариант 1 — Docker Compose (сервер с Docker)

```bash
cp .env.example .env   # заполнить AUTH_SECRET и NEXTAUTH_URL (реальный домен)
docker compose up -d --build
```

(Демо-данные из `prisma/seed.ts` — для локальной разработки; на проде сидить
их не нужно, `tsx` для сида не входит в production-образ.)

`Dockerfile` собирает production-сборку (`output: "standalone"`) и при старте
контейнера автоматически применяет миграции (`prisma migrate deploy`).

### Вариант 2 — любой Node-хостинг (Vercel, VPS и т.п.)

1. Создать базу PostgreSQL, получить `DATABASE_URL`.
2. Задать переменные окружения: `DATABASE_URL`, `AUTH_SECRET`, `NEXTAUTH_URL` (боевой домен).
3. `npm run build` (внутри выполняет `prisma generate` и `next build`).
4. Перед первым запуском — `npm run db:migrate` (`prisma migrate deploy`).
5. `npm run start`.

### Чек-лист для разработчика перед публикацией

- [ ] Завести PostgreSQL (managed или на сервере) и прописать `DATABASE_URL`
- [ ] Сгенерировать боевой `AUTH_SECRET`, задать реальный `NEXTAUTH_URL`
- [ ] Прогнать `prisma migrate deploy`
- [ ] Решить вопрос хранения фото на проде (диск с volume или S3, см. выше)
- [ ] Настроить домен и HTTPS (Nginx/Caddy/платформенный балансировщик)
- [ ] При желании — заменить/отключить сид демо-данных (`prisma/seed.ts`) перед продакшен-запуском на реальных клиентах
- [ ] Сменить пароль демо-администратора (`admin@patinastudio.ru` / `password123`) или создать нового админа и удалить демо-аккаунт через `/admin/users`

Всё остальное (код, схема БД, аутентификация, все 9 экранов макета,
CRUD строителя) готово и протестировано локально.

## Известное

- Предупреждения о `Edge Runtime` для `jose`/`bcryptjs` при сборке — ожидаемы
  для Auth.js v5 и не влияют на работу (Credentials-провайдер с bcrypt используется
  только в Node-окружении; middleware работает на облегчённой edge-safe конфигурации
  из `auth.config.ts`).
